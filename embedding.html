Embedding Bond

This guide explains how to add Bond to a C++ application. It covers getting the source code, building the Bond Runtime Library and linking it into an application, and then each step of using its API: compiling Bond source code, loading the compiled code, binding native functions, initializing global data, creating virtual machines and calling Bond functions. A complete example puts all of the steps together.

The guide shows how to do these things. For why the runtime works the way it does, including where memory is allocated, what is shared between virtual machines and the pitfalls to avoid, read The Bond Architecture. Every class and function mentioned here is described in detail in the C++ API documentation.

Overview

An application can embed Bond in one of two ways:

  • Runtime only. Bond source files are compiled ahead of time into CBO files by the bondc command line compiler, for example as a build step or in an asset pipeline. The application only loads and runs the compiled code. This is the usual choice, since it keeps the compiler out of the application entirely.
  • Runtime and compiler. The application, or a tool such as an editor, also compiles Bond source code itself through the compiler API. This is useful for tools, for live editing of scripts and for applications that accept source code at run time.

Either way, running Bond code always takes the same steps:

  1. Choose an Allocator through which Bond allocates memory.
  2. Add the Bond Standard Library, the application's native bindings and the application's CBO files to a CboLoader, and call Load() to link them into a CodeSegment.
  3. Create one or more VMs that execute the code segment.
  4. Run the code segment's static initializers once.
  5. Call Bond functions.

Figure 5 of The Bond Architecture shows these phases and the memory allocated by each of them.

Requirements

  • A C++17 compiler. Bond is developed with MSVC, GCC and Clang.
  • C++ exception support. The runtime reports errors by throwing Bond::Exception.
  • A little-endian target. bond/conf.h stops the compilation on other targets.
  • CBO files compiled for the target's pointer size. A runtime built for 64-bit pointers only loads CBO files compiled with bondc -p64, and likewise for 32 bits. By default, bondc compiles for the pointer size of the platform it runs on.

Getting the Source

The source code is hosted on GitHub. See the Download page, or clone the repository directly:

git clone https://github.com/bondscripting/bond.git

Many applications add the repository as a Git submodule or copy it into a directory of third party code, so that the version of Bond is pinned along with the application. The repository is organized as follows:

PathContents
include/bond/The public headers. The include directory is the only include path an application needs. Headers are included as "bond/<area>/<file>.h".
source/The sources of the Bond Runtime Library, including the compiled Bond Standard Library embedded as C++ arrays.
lib/include/The Bond declarations of the Bond Standard Library, such as io.bond and math.bond. Copies of them are embedded in the library, so they are only needed for reference.
tools/The command line tools: the compiler bondc, the virtual machine bond, the disassembler bondd and prettyprint.
CMakeLists.txt, Makefile.*, vs/Build files for CMake, Make and Visual Studio.
README.mdBuild instructions and the command line options of the tools.

Building and Linking

Bond builds as a library named bond, static by default. The build also produces the command line tools, which an application typically uses in its build to compile its scripts. There are several ways to build Bond and link it into an application.

CMake Subproject

For an application that is built with CMake, the simplest way to use Bond is to add its source tree as a subdirectory and link the bond_lib target:

# Bond's tests and utilities are not needed by the application.
set(BOND_BUILD_TESTS OFF CACHE BOOL "" FORCE)
set(BOND_BUILD_TEST_FRAMEWORK OFF CACHE BOOL "" FORCE)
set(BOND_BUILD_UTILS OFF CACHE BOOL "" FORCE)
add_subdirectory(external/bond)

add_executable(mygame main.cpp)
target_link_libraries(mygame PRIVATE bond_lib)

Linking bond_lib provides everything an application needs to compile against Bond: the include path, the BOND_ASSERTS_ENABLED=0 definition in all configurations except Debug, the BOND_SHARED definition when Bond is a shared library, and on MSVC, the debugger visualizers for Bond's types.

The tools remain available as the targets bondc, bond, bondd and prettyprint. They are only built if something depends on them, so leaving BOND_BUILD_TOOLS on costs nothing. It allows the application's build to compile its scripts with the freshly built bondc, as the complete example does. When cross-compiling, bondc must instead be built separately for the build machine.

Linking a Prebuilt Library

Bond can also be built on its own, and the resulting library linked like any other third party library. With CMake, run the following from the root of the Bond repository:

cmake -S . -B build
cmake --build build --config Release --target bond_lib tools

The library is written to build/lib, as libbond.a with GCC and Clang and as bond.lib with MSVC, and the tools to build/bin. Multi-configuration generators, such as Visual Studio's, add a subdirectory for the configuration, such as build/lib/Release. The --config option only applies to those generators. For the others, choose the configuration with -DCMAKE_BUILD_TYPE=Release when configuring.

The README describes the alternatives:

  • Make. Link one of the provided Makefiles, for example ln -s Makefile.gcc Makefile, then run make for the library and make tools for the tools. They are written to build/lib/bond.a and build/bin.
  • Visual Studio. Open vs/bond.slnx in Visual Studio 2026 with the Desktop development with C++ workload. The library is written to build/<Configuration>/lib.

To compile the application, add Bond's include directory to its include path, link the library, and on Windows also link shell32. The application must be compiled with the same configuration macros as the library. In particular, CMake and Visual Studio build the Release library with BOND_ASSERTS_ENABLED=0, so the application must define it too.

Adding the Sources to Your Own Build

Bond has no dependencies besides the C++ standard library, so its sources can also be compiled directly as part of the application's own build system. Compile every source/*.cpp file as C++17, with both include and source on the include path. On MSVC, also compile with /utf-8, and link shell32 on Windows. The application's own code only needs include.

Shared Library

Bond can also be built as a shared library by configuring CMake with -DBUILD_SHARED_LIBS=ON. A few additional rules apply:

  • Code that uses the shared library must be compiled with BOND_SHARED defined. CMake does this automatically for targets that link bond_lib.
  • On Windows, bond.dll must be found at run time, typically by placing it next to the executable.
  • Compile the application with the same compiler, standard library and build configuration as the library, because Bond's public types use standard library containers.
  • Native bindings that are compiled into a shared library and exported from it must be generated with bondc -e BOND_API -x bond/conf.h, so that their declarations are exported. Bindings compiled into the application itself need neither option.

Configuration Macros

Bond's compile-time configuration is defined in bond/conf.h. Each macro can be overridden on the command line, or in a header named by USER_BOND_CONFIG_HEADER, which conf.h includes before giving the macros their default values.

MacroDefaultEffect
BOND_RUNTIME_CHECKS_ENABLED1Validates the use of the runtime API, such as the types and number of arguments passed to and read from functions, and the use of null streams by the Standard Library. Violations throw a Bond::Exception. Disabling the checks removes their overhead, but makes mistakes undefined behavior.
BOND_ASSERTS_ENABLED1Enables Bond's internal consistency checks. CMake and Visual Studio set it to 0 in all configurations except Debug.
BOND_FILESYSTEM_PREFIX""A string prepended to every file name opened by a StdioStreamFactory.
BOND_MAX_PATH_LENGTH1024The maximum length of a file path, in bytes. Longer paths fail to open.
BOND_PATH_SEPARATOR, BOND_PATH_SEPARATOR_CHAR"\\" on Windows, "/" elsewhereThe file path separator, as a string and as a character. They must be overridden together.

The library and the application must be compiled with the same configuration. Parts of the runtime, such as StackFrame::GetArg() and InvocationStackFrame::PushArg(), are templates that are compiled into the application, and their behavior depends on these macros. The simplest way to keep the configuration consistent is to set it in a header named by USER_BOND_CONFIG_HEADER, or with CMake, as public compile definitions of the library, for example target_compile_definitions(bond_lib PUBLIC BOND_RUNTIME_CHECKS_ENABLED=0).

Compiling Bond Source

Compiling is optional for the application. An application that only runs code compiled ahead of time never needs the compiler. When Bond is linked statically, the linker leaves the compiler out of the executable if the application does not use it.

With bondc

The bondc command line compiler compiles one or more Bond source files into a single CBO file:

bondc -o game.cbo player.bond enemies.bond
bondc -p32 -o game32.cbo player.bond enemies.bond   # For a target with 32-bit pointers.

Code is generated for the input files only. Files that are merely included, with an include directive, provide declarations but no code. Their code must come from another CBO file that is loaded at the same time, which is how the Standard Library's headers, such as io.bond, work. The include files of the Standard Library are built into bondc, and the -I option adds directories in which to search for other included files. The README lists all of bondc's options.

With the Compiler API

The compiler consists of a Lexer, a Parser and a SemanticAnalyzer, coordinated by a FrontEnd, followed by a CodeGenerator. They are described in The Bond Architecture. The following function compiles a list of source files into a CBO file in memory. It is how bondc itself works, except that bondc writes the CBO to a file.

#include "bond/api/libinclude.h"
#include "bond/compiler/codegenerator.h"
#include "bond/compiler/compilererror.h"
#include "bond/compiler/frontend.h"
#include "bond/compiler/lexer.h"
#include "bond/compiler/parser.h"
#include "bond/compiler/semanticanalyzer.h"
#include "bond/io/memoryoutputstream.h"
#include "bond/io/memorystreamfactory.h"
#include "bond/io/stdiooutputstream.h"
#include "bond/io/stdiostreamfactory.h"

// Compiles the given source files into one CBO in cboBuffer. Returns its size, or 0 on error.
size_t Compile(Bond::Allocator &allocator, const char *const *fileNames, size_t numFiles,
    uint8_t *cboBuffer, size_t bufferSize)
{
    Bond::CompilerErrorBuffer errorBuffer;
    Bond::TokenCollectionStore tokenStore((Bond::TokenCollectionStore::allocator_type(&allocator)));
    Bond::ParseNodeStore parseNodeStore((Bond::ParseNodeStore::allocator_type(&allocator)));
    Bond::Lexer lexer(allocator, errorBuffer);
    Bond::Parser parser(allocator, errorBuffer, parseNodeStore);
    Bond::SemanticAnalyzer analyzer(errorBuffer);

    // Look for files among the embedded Standard Library headers first, then on disk.
    // Missing files return null, so that they are reported as compiler errors.
    Bond::StdioStreamFactory fileFactory(allocator, nullptr, nullptr, false);
    Bond::MemoryStreamFactory stdLibFactory(allocator, Bond::INCLUDE_FILE_INDEX, &fileFactory, false);
    Bond::FrontEnd frontEnd(allocator, tokenStore, lexer, parser, analyzer, stdLibFactory);

    for (size_t i = 0; i < numFiles; ++i)
    {
        frontEnd.AddInputFile(fileNames[i]);
    }
    Bond::TranslationUnit *translationUnits = frontEnd.Analyze();

    size_t cboSize = 0;
    if (!errorBuffer.HasErrors())
    {
        Bond::MemoryOutputStream cboStream(cboBuffer, Bond::Stream::pos_t(bufferSize));
        Bond::CodeGenerator generator(allocator, errorBuffer);
        generator.Generate(translationUnits, cboStream);
        cboSize = size_t(cboStream.GetPosition());
    }

    if (errorBuffer.HasErrors())
    {
        Bond::StdErrOutputStream errStream;
        errorBuffer.Print(errStream);
        return 0;
    }
    if (cboSize >= bufferSize)
    {
        // A MemoryOutputStream silently discards what does not fit.
        return 0;
    }
    return cboSize;
}

A few points are worth noting:

  • Compiler errors are not thrown. They are collected in the CompilerErrorBuffer, so that all of them can be reported at once. Check HasErrors() after analysis and after code generation, and print the errors with Print(), or inspect them one by one. A Bond::Exception can still be thrown for failures that are not errors in the source code, such as a stream factory that cannot open a file and is configured to throw.
  • Source files are opened through a StreamFactory. Implement the StreamFactory interface to load sources from an asset store, an archive or the network. INCLUDE_FILE_INDEX contains the include files of the Standard Library. Placing a MemoryStreamFactory for it in front of the application's factory, as above, resolves directives such as include "io.bond"; without accessing the file system.
  • Pointer size. To compile for a target whose pointer size differs from the compiler's own, pass the pointer size to both SemanticAnalyzer::SetPointerSize(), before calling Analyze(), and the CodeGenerator constructor.
  • Lifetimes. The parse trees refer to tokens and strings owned by the stores and the FrontEnd, so all of the compiler objects must stay alive until code generation is done. The resulting CBO only needs to stay alive until it has been loaded, so the buffer can be reused afterwards.
  • Allocators. Each compiler object takes an allocator. All of the compiler's memory is released when the objects are destroyed, so a pool or arena allocator that is cleared after compiling works well.

Tools can also generate native binding files from the parse trees with a NativeBindingGenerator, as bondc does when given the -b, -c, -h and -i options.

Loading a Code Segment

A CboLoader combines any number of CBO files into a single CodeSegment, binds native functions to their C++ implementations, and resolves the references between functions and data. The Bond Architecture explains what happens during loading.

#include "bond/api/libruntime.h"
#include "bond/io/stdioinputstream.h"
#include "bond/vm/cboloader.h"
#include "bond/vm/codesegment.h"

Bond::CodeSegmentHandle codeSegment;
{
    Bond::CboLoader cboLoader(allocator);
    Bond::LoadAllLibs(cboLoader);                       // The Bond Standard Library.
    cboLoader.AddNativeBinding(HOST_BINDING_COLLECTION); // The application's native functions.
    Bond::StdioInputStream hostCbo("host.cbo");          // Throws if the file cannot be opened.
    Bond::StdioInputStream gameCbo("game.cbo");
    cboLoader.AddCboFile(hostCbo);
    cboLoader.AddCboFile(gameCbo);
    codeSegment = cboLoader.Load();
} // The loader and the CBO streams are no longer needed.
  • Inputs. CBO files are added either as input streams or as buffers in memory, with AddCboFile(data, size). The loader only refers to them, and to the native binding collections, until Load() copies what it needs into the code segment. They must therefore stay valid until Load() returns, but not longer. Scoping the loader in a block, as above, releases everything that loading needed.
  • The Standard Library. Its compiled code and native bindings are built into the runtime library. LoadAllLibs() adds all of it. Alternatively, functions such as LoadLibIo() and LoadLibMath() add individual libraries. In that case, add every library whose include file the application's scripts include, directly or indirectly. For example, io.bond includes memory.bond.
  • Order. Static initializers run in the order in which their CBO files were added. Add libraries before the code that depends on them.
  • Allocators. The code segment is allocated from the loader's allocator. The second constructor, CboLoader(tempAllocator, permAllocator), uses separate allocators for the temporary data of loading and for the long-lived code segment.
  • Errors. Load() throws a Bond::Exception if a CBO file is malformed, was compiled for a different pointer size or format version, or if a function or global is defined twice, a referenced name is not defined, or a native function has no binding.

The CodeSegmentHandle returned by Load() owns the code segment and frees it when it is destroyed. The code segment must outlive every VM that uses it, so declare the handle before the VMs. Its functions are looked up with GetFunction(), and its global constants with GetDataEntry(), by qualified name with the elements separated by dots, such as "Game.Score". Both return null if there is no such name.

Native Functions

Native functions are Bond functions implemented in C++. They are how Bond scripts call into the application. The Bond side of native functions and structs, the C++ functions that implement them and the naming conventions for member functions, getters and setters are described in the Native Blocks section of the language reference. This section describes how they fit into an application.

Declaring, Generating and Registering

Native functions are declared in a native block, usually in a file of their own:

// host.bond
native
{
    namespace Host
    {
        int GetLevel();
        void Log(const char *message);
    }
}

bondc compiles the file and generates the C++ declarations of the native functions, along with a native binding collection that maps their names to their implementations:

bondc -o host.cbo -b HOST_BINDING_COLLECTION -c hostbindings.cpp -h hostbindings.h -i hostbindings.h host.bond

The generated header looks like this:

#ifndef HOSTBINDINGS_H
#define HOSTBINDINGS_H

#include "bond/api/nativebinding.h"

extern const Bond::NativeBindingCollection HOST_BINDING_COLLECTION;

namespace Host
{
void GetLevel(Bond::StackFrame &frame);
void Log(Bond::StackFrame &frame);
}

#endif

The application compiles hostbindings.cpp, implements the declared functions, and registers the collection with the CboLoader, as shown in the previous section. Scripts that use the functions include host.bond.

The CBO compiled from the native declarations must be loaded. Including host.bond in a script makes the native functions known to the compiler, but does not generate them into the script's CBO file. Unless host.cbo is also loaded, or host.bond is passed to bondc as an input file along with the scripts, loading fails with an error such as Unresolved qualified name 'Host.GetLevel'.

The loader checks the bindings when it loads the code. Loading fails if a native function has no binding, or if a binding names a function that is not a native function of the loaded code. Register a binding collection only together with the CBO file that declares its functions.

Implementing Native Functions

Each native function receives the StackFrame of its call, from which it reads its arguments and through which it sets its return value:

#include "hostbindings.h"
#include "bond/vm/vm.h"
#include <cstdio>

namespace Host
{

void GetLevel(Bond::StackFrame &frame)
{
    frame.SetReturnValue(int32_t(3));
}

void Log(Bond::StackFrame &frame)
{
    const char *message = frame.GetArg<const char *>(0);
    printf("[log] %s\n", message);
}

}
  • Types. GetArg<T>(index) must use the C++ type that corresponds to the parameter's Bond type, as listed under Primitive Types. For example, int is int32_t, long is int64_t and bool is uint8_t. Integer types match any Bond integer type of the same size, regardless of signedness. Pointers are passed as pointers, and structs can be passed and returned by value as any trivially copyable C++ type of the same size. With runtime checks enabled, a mismatch throws a Bond::Exception.
  • Member functions. For native member functions, getters and setters, argument 0 is the this pointer. See Implementing and Binding Native Code.
  • The VM. frame.GetVM() returns the VM executing the call. From it, a native function can get the VM's allocator with GetAllocator(), its standard streams with GetStdOut(), GetStdErr() and GetStdIn(), its StreamFactory, and its CodeSegment.
  • Application state. Bond has no global variables, and native functions receive only their StackFrame. To reach application state, a native function can use state of its own that is keyed by the VM, or the script can pass it a pointer that it received from the application.
  • Allocating on behalf of the caller. Memory that should live until the calling Bond function returns can be registered with the Collector of the caller's frame, frame.GetVM().GetCallerStackFrame().GetCollector(). This is how the Standard Library's collected allocation and stream functions work; see source/libmemory.cpp. It is the basis of scope-based resource management.
  • Errors. frame.GetVM().RaiseError(format, ...) throws a Bond::Exception whose message is followed by a dump of the Bond call stack.
  • Calling back into Bond. A native function can call Bond functions on the same VM. An error raised in the nested call propagates through the native function, so it must be exception-safe.

Writing a Binding Collection by Hand

A binding collection is just an array of name and function pairs, so it can also be written by hand, for example for a few functions in a test:

const Bond::NativeFunctionBinding HOST_BINDINGS[] =
{
    {"Host.GetLevel", Host::GetLevel},
    {"Host.Log", Host::Log},
};

const Bond::NativeBindingCollection HOST_BINDING_COLLECTION = {HOST_BINDINGS, 2};

Names are fully qualified, with their elements separated by dots. Generated bindings are less error-prone, since they are always consistent with the Bond declarations.

Running Static Initializers

Global constants whose values are only known at run time, such as const int BONUS = Square(10);, are initialized by static initializers, which the compiler generates. The application must run them, once, after loading and before calling any other Bond function:

codeSegment->CallStaticInitializers(vm);

Any VM that uses the code segment can run them. Any memory that the initializers allocate comes from that VM's allocator.

Static initializers must run exactly once per code segment. If they are never run, the affected constants silently read as zero. If they are run again, or while another VM is running code, they rewrite data that every VM shares. See Global Data and Static Initialization and Pitfalls.

Creating a Virtual Machine

A VM executes the functions of a code segment:

#include "bond/io/stdiooutputstream.h"
#include "bond/vm/vm.h"

Bond::StdOutOutputStream outStream;
Bond::StdErrOutputStream errStream;
Bond::VM vm(allocator, *codeSegment, 64 * 1024, nullptr, &outStream, &errStream);
ParameterDescription
allocatorThe allocator from which the VM's stack is allocated. The Standard Library also allocates from it, as do native functions that use GetAllocator().
codeSegmentThe code segment to execute. It is not copied, so it must outlive the VM.
stackSizeThe size of the VM's stack in bytes, which is fixed for the lifetime of the VM. The bond tool uses 256 kB by default.
stdIn, stdOut, stdErrOptional. The streams returned by the Standard Library's StdIn(), StdOut() and StdErr(). Any InputStream or OutputStream will do, so output can be redirected to a log or captured in memory.
streamFactoryOptional. The factory through which the Standard Library opens files. A StdioStreamFactory opens files on disk, optionally relative to a root path. A custom factory can restrict or redirect the files that scripts can access.
  • Missing streams. The streams and the factory default to null. With runtime checks enabled, a script that uses a missing stream, or that opens a file without a factory, fails with a Bond::Exception. Without runtime checks, it crashes. Pass the streams that the application's scripts are expected to use.
  • Lifetimes. The VM owns none of the objects passed to it. The allocator, the code segment, the streams and the factory must all outlive it.
  • Stack size. Creating a VM makes exactly one allocation: its stack. The stack must hold the deepest chain of calls the scripts make. Each Bond call also uses the native stack of the thread that runs the VM, so a very large VM stack used for deep recursion can overflow the native stack first. See Pitfalls.
  • Many VMs, many threads. Any number of VMs can share one code segment, each costing only its stack. A VM must only be used by one thread at a time, and Bond performs no synchronization. See Sharing a Code Segment Between VMs.

Calling Bond Functions

The simplest way to call a Bond function is VM::CallFunction(), which takes a pointer to where the return value is stored, followed by the arguments. VM::CallVoidFunction() does the same for functions that return void. Functions can be identified by name, but looking them up once and reusing the const Function * avoids a binary search on every call:

const Bond::Function *score = codeSegment->GetFunction("Game.Score");
if (score != nullptr)
{
    int32_t result = 0;
    vm.CallFunction(*score, &result, int32_t(5));
}

vm.CallVoidFunction("Game.Reset");

When the arguments are not all known in one place, an InvocationStackFrame builds the call argument by argument:

int32_t result = 0;
{
    Bond::InvocationStackFrame frame(vm, *score, &result);
    frame.PushArg(int32_t(5));
    frame.Call();
}

An InvocationStackFrame pushes a frame onto the VM's call stack when it is constructed and pops it when it is destroyed, so it should be a local variable that goes out of scope right after the call.

  • Argument types. Arguments follow the same rules as native function arguments. Use fixed-width types, such as int32_t(5) rather than 5L, whose size differs between platforms. Pointers to the application's data can be passed directly. Bond reads and writes through them like C does, without conversion or copying.
  • Return types. Integers smaller than 32 bits are returned widened to 32 bits, so a Bond function that returns bool, char or short must be received in an int32_t or a uint32_t. With runtime checks enabled, a smaller integer type is rejected at compile time.
  • Checks. With runtime checks enabled, a wrong number of arguments, or a wrong argument or return type, throws a Bond::Exception before the function runs. For example: Attempt to call a function with incorrect return address type. Expected 'int32_t'.
  • Entry points. Bond has no fixed entry point. An application calls whatever functions it chooses, any number of times. The bond tool, for example, calls main with either no parameters or argc and argv, depending on its signature; see tools/bond.cpp.

Handling Errors

All runtime errors are reported by throwing a Bond::Exception. One handler around loading and calling covers everything:

try
{
    // Load, create the VM, run static initializers and call functions.
}
catch (const Bond::Exception &e)
{
    fprintf(stderr, "%s\n", e.GetMessage());
}
  • Errors raised while Bond code runs include a dump of the Bond call stack in the message. The message is stored in a fixed buffer of Exception::MESSAGE_BUFFER_LENGTH bytes inside the exception, so very long messages are truncated.
  • As the exception propagates, the VM's call stack is restored and collected resources are released, so the VM can be used again for further calls. Memory that the script allocated with Allocate() and had not freed is leaked, as in C.
  • Bond has no exception handling of its own, and a Bond function cannot catch an error. See Errors.

A Complete Example

The following example puts the steps together. It uses the host.bond file from the Native Functions section and a script that uses it:

// game.bond
include "io.bond";
include "host.bond";

namespace Game
{
    int Square(int x)
    {
        return x * x;
    }

    // Not a compile-time constant, so it is set by the static initializer.
    const int BONUS = Square(10);

    int Score(int hits)
    {
        Host::Log("Scoring");
        const int score = hits * Host::GetLevel() + BONUS;
        Bond::StdOut()->PrintStr("Score: ")->PrintI(score)->PrintC('\n');
        return score;
    }
}

The application implements the native functions, loads host.cbo and game.cbo, and calls Game.Score:

// main.cpp
#include "hostbindings.h"
#include "bond/api/libruntime.h"
#include "bond/io/stdioinputstream.h"
#include "bond/io/stdiooutputstream.h"
#include "bond/systems/defaultallocator.h"
#include "bond/systems/exception.h"
#include "bond/vm/cboloader.h"
#include "bond/vm/codesegment.h"
#include "bond/vm/vm.h"
#include <cstdio>

// Implementations of the native functions declared in host.bond.
namespace Host
{

void GetLevel(Bond::StackFrame &frame)
{
    frame.SetReturnValue(int32_t(3));
}

void Log(Bond::StackFrame &frame)
{
    const char *message = frame.GetArg<const char *>(0);
    printf("[log] %s\n", message);
}

}

int main()
{
    Bond::DefaultAllocator allocator;

    try
    {
        // 1. Load the CBO files into a code segment.
        Bond::CodeSegmentHandle codeSegment;
        {
            Bond::CboLoader cboLoader(allocator);
            Bond::LoadAllLibs(cboLoader);
            cboLoader.AddNativeBinding(HOST_BINDING_COLLECTION);
            Bond::StdioInputStream hostCbo("host.cbo");
            Bond::StdioInputStream gameCbo("game.cbo");
            cboLoader.AddCboFile(hostCbo);
            cboLoader.AddCboFile(gameCbo);
            codeSegment = cboLoader.Load();
        } // The loader and the CBO streams are no longer needed.

        // 2. Create a VM with a 64 kB stack. Bond's StdOut() writes to outStream.
        Bond::StdOutOutputStream outStream;
        Bond::StdErrOutputStream errStream;
        Bond::VM vm(allocator, *codeSegment, 64 * 1024, nullptr, &outStream, &errStream);

        // 3. Initialize global constants, such as Game::BONUS.
        codeSegment->CallStaticInitializers(vm);

        // 4. Look up a function once, then call it.
        const Bond::Function *score = codeSegment->GetFunction("Game.Score");
        if (score == nullptr)
        {
            fprintf(stderr, "Game.Score not found\n");
            return 1;
        }
        int32_t result = 0;
        vm.CallFunction(*score, &result, int32_t(5));
        printf("Result: %d\n", int(result));
    }
    catch (const Bond::Exception &e)
    {
        fprintf(stderr, "%s\n", e.GetMessage());
        return 1;
    }

    return 0;
}

The CMake project builds Bond as a subproject, uses the bondc it builds to compile the scripts and generate the bindings, and builds the application:

cmake_minimum_required(VERSION 3.16)
project(BondExample LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

set(BOND_BUILD_TESTS OFF CACHE BOOL "" FORCE)
set(BOND_BUILD_TEST_FRAMEWORK OFF CACHE BOOL "" FORCE)
set(BOND_BUILD_UTILS OFF CACHE BOOL "" FORCE)
add_subdirectory(external/bond)

# Compile the scripts and generate the native bindings with bondc.
set(GEN_DIR ${CMAKE_CURRENT_BINARY_DIR})
add_custom_command(
  OUTPUT ${GEN_DIR}/host.cbo ${GEN_DIR}/hostbindings.cpp ${GEN_DIR}/hostbindings.h
  COMMAND bondc -o host.cbo -b HOST_BINDING_COLLECTION -c hostbindings.cpp
          -h hostbindings.h -i hostbindings.h ${CMAKE_CURRENT_SOURCE_DIR}/host.bond
  DEPENDS bondc ${CMAKE_CURRENT_SOURCE_DIR}/host.bond
  WORKING_DIRECTORY ${GEN_DIR}
)
add_custom_command(
  OUTPUT ${GEN_DIR}/game.cbo
  COMMAND bondc -o game.cbo ${CMAKE_CURRENT_SOURCE_DIR}/game.bond
  DEPENDS bondc ${CMAKE_CURRENT_SOURCE_DIR}/game.bond ${CMAKE_CURRENT_SOURCE_DIR}/host.bond
  WORKING_DIRECTORY ${GEN_DIR}
)

add_executable(example main.cpp ${GEN_DIR}/hostbindings.cpp ${GEN_DIR}/game.cbo)
target_include_directories(example PRIVATE ${GEN_DIR})
target_link_libraries(example PRIVATE bond_lib)

Listing game.cbo among the sources of the executable makes the build generate it, even though it is not compiled. The CBO files are written to the build directory, and the program opens them by relative path, so run it from there. With a multi-configuration generator, such as Visual Studio's, the executable is in a subdirectory for the configuration:

cmake -S . -B build
cmake --build build --config Release
cd build

Other Things Worth Knowing

  • Custom allocators. All of Bond's memory goes through the Allocator interface. An implementation provides Allocate(), AllocateAligned(), Free() and FreeAligned(). The provided DefaultAllocator uses new and delete. It counts outstanding allocations, which GetNumAllocations() returns, making it easy to check for leaks in tests. The count is not synchronized, so the DefaultAllocator is not thread-safe.
  • Custom stream factories. Every file that the compiler or the Standard Library opens goes through a StreamFactory. Factories can be chained through their delegate factory, as the compiler example does.
  • UTF-8 console output on Windows. Bond strings are UTF-8. A console application on Windows can create a Bond::Utf8ConsoleOutput object, declared in bond/tools/commandline.h, to make the console display UTF-8 output while it exists. Libraries that embed Bond should leave the console to their host application.
  • Versions. bond/version.h defines the version of Bond, Bond::VERSION_STRING, and the range of CBO format versions the runtime can load. The CBO format has not been finalized, so rebuild all CBO files when upgrading Bond.
  • Debugging. With MSVC, the CMake build embeds debugger visualizers for Bond's types, such as VMs and stack frames. While a VM is stopped in a native debugger, BondDebugDumpCallStack(&vm) returns its Bond call stack as a string. The bondd tool disassembles CBO files, and the @ pc offsets in call stack dumps refer to its listings.
